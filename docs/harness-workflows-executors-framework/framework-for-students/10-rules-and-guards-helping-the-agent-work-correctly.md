# 10. Rules and Guards: Helping the Agent Work Correctly

Imagine your class building a wooden bridge.

The teacher explains how to build strong supports and gives one requirement: the bridge must hold a book. After the work, someone tests it and records what happened.

The instructions help you build. The requirement says what matters. The test gives evidence about the result.

**A guard connects these things: guidance, rules, checks, and a decision about what happens next.**

This chapter describes the proposed kushibot framework. The examples explain the design; they do not imply that these checkers are already implemented.

## A Guard Is More Than a Reminder

Suppose we tell a coding agent:

> Follow good object-oriented design.

That may help, **but it does not tell us which requirements were evaluated or what evidence supports the result.** The agent saying “I followed OOP” does not prove it.

A guard makes the expectations and evaluation explicit:

```text
Guard: Object-oriented design
Skill: Explain how to write classes with clear responsibilities
       and receive external collaborators through constructors.
Rules: Services receive their external collaborators.
       Each class has a clear responsibility.
Checks: Inspect the relevant code and report evidence for each rule.
After checking: Apply the configured policy to continue, request a fix,
                seek further review, or stop.
```

“External collaborators” means things a service uses, such as a database repository or a login-provider client.

A useful guard can answer: 

**What did we ask the agent to follow? 
What did we actually check? 
What did we find?**

## Who Defines the Rules? Does the LLM Generate Them?

**Developers define the guard rules in trusted application configuration before the agent starts. The LLM does not invent the requirements it will be judged against.**

For example, a developer registers an OOP guard containing this rule:

```text
Rule ID: oop.constructor-injection
Requirement: Services must receive their external collaborators
             through their constructors.
```

The developer also supplies the skill instructions, **connects the rule to its checks,** and configures whether a violation blocks progress.

The LLM has three roles in this process:

1. **Recommend relevant guards:** Given an assignment, recommend which existing registered guards apply. Trusted policy validates the selection and keeps required guards.
2. **Follow the rules:** Use the selected guard's instructions and rules while writing code.
3. **Review against the rules:** When assigned a review, inspect the code and report whether evidence supports compliance or a violation of the existing rules.

**A review finding is generated by the LLM; the rule being checked was defined by the developer.** Programmed checkers can also evaluate rules without LLM judgment.

For example, the developer defines the constructor-injection rule. The coding agent writes LoginService. A reviewing agent then reports: “LoginService creates its own provider client, which violates oop.constructor-injection,” and cites the relevant code. The reviewer discovered a violation; it did not create a new requirement.

An LLM can help a developer draft proposed rules, but those suggestions become enforced rules only after they are adopted into trusted configuration. During a run, the LLM cannot rewrite, weaken, or remove a required rule to make its work pass.

## How Guards, Skills, and Rules Work Together

These are related parts, not three names for the same thing:

| Part               | Its job                                                  | OOP example                                                                           |
| ------------------ | -------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| Skill              | Teach the agent how to do the work.                      | Explain constructor injection and show examples.                                      |
| Rule               | State a specific requirement the work should meet.       | A service must receive its provider collaborator rather than construct it internally. |
| Check              | Evaluate a rule and produce evidence.                    | Read the service and application assembly code to see where the provider is created.  |
| Guard              | Package the guidance, rules, and checks for one concern. | An OOP guard connects OOP instructions with design checks.                            |
| Enforcement policy | Decide what follows the findings.                        | A required violation leads to a bounded correction before continuing.                 |

**The skill guides the work before and during coding. The checks evaluate the resulting work afterward. The rules connect the two.**

**A rule is a named requirement, not necessarily executable code.** Some rules can be checked by a program; others need a review. Naming a rule makes it possible to connect a finding to the exact requirement that was evaluated.

For example:

```text
Rule ID: oop.constructor-injection
Requirement: Services receive their external collaborators.
Finding: LoginService creates its own provider client.
Evidence: Reference to the constructor in the checked code.
```

A skill on its own can provide useful instructions. 
A guard adds explicit evaluation and handling of the results. 

Supplying either one does not grant the agent additional tools or permissions.

## What Is the Difference Between a Rule and a Skill?

**A rule says what must be followed. A skill explains how to do it.**

Imagine learning to cook:

- **Rule:** Wash your hands before preparing food.
- **Skill:** Instructions showing you how to wash your hands properly and prepare food safely.

The same distinction applies to a coding agent:

- **Rule:** A service must receive its database collaborator through its constructor.
- **Skill:** Explain constructor injection, show an example, and guide the agent through applying it.

A skill can include rules alongside explanations and examples. The difference is their purpose: **the rule states the requirement; the skill helps the agent meet it.**

Neither one proves the agent followed the requirement. That is why the guard also needs a check.

## Can One Skill Have Multiple Rules?

**Yes. One skill can teach the agent how to follow several related rules.**

For example, an OOP skill can explain these developer-defined rules with instructions and examples:

- Give each class a clear responsibility.
- Receive external collaborators through constructors.
- Keep class-owned helpers private.
- Prefer composition over deep inheritance.

In the OOP guard, each requirement has its own named rule and appropriate checks. The skill teaches them together, but **each rule is evaluated separately and can have a different outcome.**

Imagine reviewing LoginService:

| Rule | What the check found | Outcome |
| --- | --- | --- |
| Receive external collaborators through constructors. | The service receives its provider and repository through its constructor. | Passed |
| Give each class a clear responsibility. | Review found unrelated report-generation work mixed into login handling, with references to the relevant methods. | Failed |
| Keep class-owned helpers private. | The reviewer could not access a required helper file, so the evidence is incomplete. | Unable to evaluate |
| Prefer composition over deep inheritance. | No inheritance is involved, and the configured applicability policy treats this rule as irrelevant to this change. | Not applicable |

These are illustrative outcomes, not automatic verdicts based on the rule names. Each check must supply evidence and explain its coverage; a not-applicable outcome must also be justified under policy.

**The skill does not get one blanket “passed” label.** Its associated guard reports which rules passed, failed, did not apply, or could not be evaluated. Trusted policy then decides whether the combined results allow the workflow to continue.

## Which Parts Are Deterministic, and Which Need an Agent?

**Deterministic checks follow a precise programmed procedure. Agent reviews interpret the code and make a judgment.** A guard can use both.

| Example | Who evaluates it? | What it establishes |
| --- | --- | --- |
| Run the project's configured lint check. | An actual checking tool. | The lint diagnostics for the checked code and configuration. |
| Detect direct `new PrismaClient()` calls in specified service files using a code parser. | A programmed structural checker. | Whether that particular construction pattern occurs in those files. |
| Decide whether a class mixes unrelated responsibilities. | A reviewing agent, or a human where configured. | An evidence-based design assessment, with possible uncertainty. |

“Review the design” is an agent task unless we define an exact programmed procedure. A narrow structural check does not prove that the whole design is good.

The coding agent follows the skill. A reviewing agent may evaluate design rules. Tools produce their actual check results. The framework coordinates these checks and applies the configured policy; it must not turn an agent's opinion into a claimed tool result.

## How Does the Framework Choose Guards?

Different assignments need different guards. Editing a login service may need OOP and lint guards. Changing a database schema may also need a database guard.

Developers configure the available guards, their rules, and which guards are required. The LLM selects from these existing candidates; it does not generate new rules during selection. Then:

1. The framework collects the assignment and relevant workspace information.
2. DecisionUnit recommends relevant guards from the enabled, registered candidates.
3. Trusted selection policy validates the recommendation and preserves required guards.
4. The worker receives the selected skills and applicable rules before doing the work.

```text
Required guards + accepted relevant recommendations
                         ↓
              Guards used for the assignment
```

**The relevance decision uses agent judgment; preserving required guards and validating the selection use programmed policy.** The model cannot remove a required guard.

After editing, the actual changes may reveal another relevant guard. For example, the agent may have changed a database schema as well as the login service. The framework can add the relevant guidance and checks before accepting the work.

If selection cannot run, required guards remain required. The framework follows its configured fallback and keeps unresolved selection visible; failure does not mean “no guards apply.”

## The Four Check Outcomes

Each rule/check evaluation reports one of these outcomes:

| Outcome | Meaning |
| --- | --- |
| Passed | The rule was evaluated with no detected violation under the stated coverage. |
| Failed | Evidence supports a violation. |
| Not applicable | Scope and policy justify that this rule does not apply. |
| Unable to evaluate | Missing tools, missing evidence, invalid output, or another problem prevented evaluation. |

**Coverage means what was actually examined:** which files, which rules, and which version of the code.

For example:

- **Passed:** The configured lint check ran on the required files and found no violations.
- **Failed:** Review found that LoginService creates a provider client internally, contrary to the applicable dependency rule.
- **Not applicable:** A database-schema rule does not apply because no schema-related work is involved, as justified by the evidence and policy.
- **Unable to evaluate:** The lint tool is missing, or the reviewer could not read a required file.

These are evaluation outcomes, not lifecycle stages such as “waiting” or “running.” A single guard may have several rule outcomes: lint could pass while a design review remains unable to evaluate. **One passing check does not make every rule pass.**

**The report records the outcomes, findings, evidence, and coverage. A model saying “no issues” is insufficient if it never examined the required code.**

## Follow an OOP Guard Through a Login Change

1. **Select:** The assignment is to add Google login. The effective guard set includes OOP and lint.
2. **Guide:** The coding agent **receives the skills and rules**. **It knows that LoginService should receive its provider collaborator.**
3. **Check:** After editing, the r**eviewing agent inspects the relevant code**. The actual lint tool also runs.
4. **Report:** **Review finds a provider client created inside LoginService and cites the constructor. That rule fails.** Lint passes for its checked scope.
5. **Decide:** The **configured policy requires the design issue to be fixed.** If allowance remains, the workflow gives the coding agent a focused correction assignment with the rule and evidence.
6. **Recheck:** The agent changes the service to receive its collaborator. The affected checks evaluate the updated code, and their new reports identify that version.
7. **Continue:** **The workflow continues when the required conditions are met**. If a mandatory check cannot run or correction limits are exhausted, it preserves the unresolved result instead of inventing a pass.

The guard identifies and evaluates requirements. The coding worker makes the changes. The policy controls whether the workflow can continue.

Passing these guards still does not prove that Google login works: behavior tests and other required verification remain necessary. It also does not authorize publishing the changes.

## One Policy Agreement for Selection and Enforcement

The guard-selection policy receives registered candidates and required rules and returns the effective set. The enforcement policy receives actual check reports and returns continue, fix, review, or stop. Both use Policy<TInput, TOutput> and apply(). The guard runner performs checks, and the runtime preserves mandatory coverage.

For the shared technical contract, see [One Shared Policy Concept](../31-shared-policy-concept.md).

## Remember These Ideas

- **Skill:** How should the agent do the work?
- **Rule:** What developer-defined requirement should the work meet?
- **Check:** What evidence shows whether that rule was followed?
- **Guard:** Bring the guidance, rules, and checks together for one concern.
- **Policy:** What should happen after the reported outcome?

Developers define the rules. The LLM recommends relevant guards, follows their rules, and can review the code against them. Trusted policy controls which requirements remain mandatory and what happens after checking.

Reading instructions is not proof of following them. A useful guard makes the evaluated rules, evidence, and remaining uncertainty visible.
